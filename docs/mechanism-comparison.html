What is being compared

1. The comparison matrix

Four mechanisms for the same problem: an Oracle-backed A1 transaction changes state, and something must turn that into an event. A1 writes it from a PL/SQL trigger onto Oracle AQ. A2 writes it from the application into a transactional outbox table, relayed by a poller. A3 writes nothing — Debezium reads the change directly from the redo log via LogMiner. HYBRID combines A2's outbox with A3's relay.

How each method actually reaches Kafka

The four methods differ in exactly one place: what happens inside the same database commit as the business write, before anything leaves for Kafka. Three of them add a step there; one adds nothing. Only the step highlighted below was tested by breaking it (fault F8) — and breaking it stopped real payments.

Section 2.1 · the trade-off is real

2. Latency spans 560×, and it runs opposite to redo cost

Same events, same workload. AQ is notified at commit (DBMS_AQ.DEQUEUE blocks, no poll). The outbox relay asks repeatedly — half a 200 ms poll interval expected, matching the measured 128 ms. Both Debezium pipelines wait for the LogMiner cycle — seconds, not milliseconds.

Speed of delivery is bought with work done inside the transaction. AQ is fastest and most expensive to write (+171% redo); CDC is slowest and free to the writer (+0.7%, not distinguishable from the uninstrumented control).

CDC's cost is not zero — it is moved, not removed (claim C2). Database CPU rises at 13.0 CPU-seconds per GB of discarded redo (95% bootstrap CI 5.86–18.62), and at the highest tested level 79% of CDC's database-side cost was spent reading redo that never became an event. Cheap in the transaction, expensive in the instance — a different budget line, not an absent one.

Section 2.2 · strongest methodological result in the thesis

3. Counting events does not measure an event pipeline

First CDC run: 9,003 messages for 9,003 committed transitions. Counts matched exactly. Every message was well-formed JSON. Connector RUNNING, lag flat, zero warnings. Every conventional health signal said the pipeline was perfect.

Two thirds of those messages looked like this:

{ "TXN_ID": "0", "TXN_REF": "", "AMOUNT": "0.0000", "STATUS": "VALIDATED" }

Minimal supplemental logging means the redo record for an UPDATE carries only the changed columns; Debezium fills the rest with type defaults. Only reconciliation against an independent ground truth on a semantic key exposed it — no count, no health check, no lag metric could. Fixed with ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS; the same run then reconciled 9,003/9,003 with zero loss, zero phantoms.

A pipeline can deliver exactly the right number of structurally valid, semantically empty messages, and every conventional health signal will report success.

Section 2.3 · fault F11 — the condition, measured

4. The hybrid's coverage is an organisational property, not an architectural one

An end-of-day PL/SQL batch writes A1 transactions directly, bypassing the application entirely (~87,000 transitions):

ModeMissingLoss rate
AQ0 / 86,9900%
CDC0 / 86,9940%
Outbox (WRAPPER_B3)59,983 / 86,98469.0%
HYBRID59,990 / 86,99169.0%

The hybrid failed identically to the plain outbox — not predicted in advance. Writer coverage is not a property of the architecture; it is a property of whether an organisation modifies every writer to go through the shared contract. In a core bank with decades of batch jobs, that cannot be guaranteed. Only the trigger and the redo log see everything a writer does, modified or not.

6. Three predictions were made in advance and refuted

Of seven statements the fault matrix set out to test: three established, one supported with a stated statistical limit, three refuted — two of them contradicting this thesis's own predictions, made before any of it was built.

Prediction (stated in advance)Result
Purging every archive after 10 forced log switches (F4) would cause loss Refuted — 0% loss observed
Holding a transaction 240s past a 180s configured retention (F5) would discard it Refuted — not discarded
Relaying the outbox with Debezium (HYBRID) "cuts end-to-end latency" (own prior analysis) Refuted — arrives 25× later than AQ; benefit is DB protection, not speed

A refuted prediction, tested under a controlled fault injection with a stated methodology, is what distinguishes this from a report that only confirms documented behaviour.

The single most important trade-off: availability coupling. AQ is the only mechanism where a defect in the observability path stopped 40% of payments (fault F8). For a core banking system that is not a performance characteristic — it is a category of outage the other three approaches structurally cannot produce.

8. Exact experimental setup and configuration

Every value below was read from the live Oracle instance or the checked-in configuration that produced §1's numbers. Full detail with file paths: docs/empirical_comparison_results.md §6.

Harness. 5 repetitions per mode, 50 TPS, 120 s steady-state / 180 s fault duration, fault injected at 60 s. Repetitions interleaved (rep 1 of every mode, then rep 2, …) and mode order rotated per repetition, so no mode is confounded with time-of-day drift or a fixed cold-cache position.

./scripts/run-experiment.sh --mode WRAPPER_B3 --profile P1 --tps 50 --duration 120s --rep 1

Stated honestly: 10 MB redo groups switch every few seconds under AQ's +171% redo load, visible as Checkpoint not complete in the alert log. Every mode runs against the same log configuration, so the relative comparison holds; the absolute redo percentages are specific to a small-redo-log instance.

Debezium connector (CDC) — key parameters:

The 180,000 ms retention is fault F5's exact target — a transaction held open past it is silently discarded by design, confirmed by the fault test. HYBRID differs by capturing A1_EVENT_OUTBOX instead, through Debezium's EventRouter outbox transform, with table.field.event.timestamp deliberately left unset (setting it produced a physically impossible −1 ms median latency in an earlier draft).

Fault injection — exact mechanics (scripts/inject-fault.sh):

FaultExact action
F8Recompiles PKG_A1_EVENT with its type-resolution function forced to return an invalid value, making the capture package invalid mid-run
F11PKG_SYNTH_DATA.generate_transactions(p_count=20000, p_source='BATCH_EOD') — writes TXN_A1 directly, bypassing the app and the outbox contract
F11BSame batch, with p_emit_outbox => TRUE — the same writer honouring the shared contract
F4/F4RStop Connect → switch/archive the redo log 10×→ RMAN DELETE ARCHIVELOG ALL → restart Connect
F5/F5R5,000-row transaction held open 240 s (60 s past the 180 s retention) before commit

Approach 1 (trigger+AQ): queue table A1_EVT_QT (payload SYS.AQ$_JMS_TEXT_MESSAGE), queue A1_EVT_Q, compound trigger TRG_TXN_A1_AQ buffering per-row and emitting per-statement, DBMS_AQ.ENQUEUE with visibility => ON_COMMIT. Bridge dequeues batches of up to 500 messages (500 ms receive timeout), single-threaded to preserve enqueue order.

Approach 2 (outbox): table A1_EVENT_OUTBOX (insert-only), write contract EMIT_A1_EVENT — no autonomous transaction, the caller's transaction owns the commit. OutboxRelay polls every 200 ms, batch size 500.

Objection: "This is all synthetic / simulated, not a real bank"

Say:

"The workload generator is synthetic — a real bank's transaction mix was not used, on information-security grounds. But the measurement is real: the same Oracle instance, the same Debezium connector, the same Kafka cluster measured the redo log, the commit counters, and the wall-clock latency. The workload is synthetic; the physics — redo bytes written, milliseconds elapsed — is not."

Objection: "Only 5 repetitions — is that enough?"

Say:

"For the size of the effects being tested, yes — AQ's +171% redo against CDC's +0.7% is not a difference five repetitions leaves in doubt, and the exact permutation test's own floor (p=0.0079 at n=5) is stated rather than hidden. Where an effect is small — CDC's redo change is not statistically significant at n=5 — that is reported as non-significant, not rounded up to a claim."

Objection: "Throughput ceiling isn't measured — that's a gap"

Say:

"Correct, and stated as a limitation, not hidden. All four modes sustained 45.6 tps with no degradation at the tested load; the saturation point (profile P2) was not run. What is known: the naive after-commit variant — not one of the four in this table — was already the binding constraint at 50 tps, which is why 50 rather than 200 was chosen as the operating point."

Objection: "C2 — I heard one of your analyses was wrong at first"

Say:

"Yes — a regression in the first C2 pass used two variables that were arithmetically identical, which mechanically produces a false rejection. Caught during review, and the corrected analysis is what's reported: 13.0 CPU-seconds per GB of discarded redo, CI 5.86–18.62. C2b's control separately failed and is reported as inconclusive rather than patched to look conclusive."

How does this connect to the credit-process chapter (7)?

Say:

"Chapter 7 measures where time goes in a credit application from stage-transition events. Every figure there is a difference between two timestamps. If a mechanism drops one transition, the case silently appears to have skipped a stage and the previous stage's duration is inflated — no error, no alarm, just a wrong number that looks right. Chapters 5–6 establish which mechanism can be trusted not to do that before chapter 7 uses one."
